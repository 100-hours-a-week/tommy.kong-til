## 3. GET, POST, PUT, DELETE에 대해 설명해주세요.
각각은 HTTP 메서드의 일부이며 웹 서버에 요청할 때 사용 
- GET 
	- 특정 서버에게 특정 리소스를 요청하는 메서드
	- 요청 데이터는 URL의 쿼리 스트링으로 전달됨
- POST
	- 서버에게 새로운 리소스를 생성하거나 기존 리소스를 수정하라고 요청하는 메서드 
	- 요청 데이터는 HTTP 바디에 담겨 저장됨
- PUT
	- 서버에게 특정 리소스를 전체적으로 교체하거나 생성하라고 요청하는 메서드 
	- 요청 데이터는 HTTP 바디에 담겨 저장됨
- DELETE
	- 서버에게 특정 리소스를 삭제하라고 요청하는 메서드 
	- 요청 데이터는 URL의 쿼리 스트링으로 전달됨

| HTTP 메소드 | 안전  | 멱등  | 캐시 가능 |
| -------- | --- | --- | ----- |
| GET      | O   | O   | O     |
| POST     | X   | X   | O     |
| PUT      | X   | O   | X     |
| DELETE   | X   | O   | X     |

POST vs PUT

| 항목               | POST                 | PUT                    |
| ---------------- | -------------------- | ---------------------- |
| 역할               | 새 리소스를 생성하거나 작업을 위임  | 리소스를 전체 교체하거나 생성(덮어쓰기) |
| 멱등성 (idempotent) | ❌ (요청할 때마다 다른 결과 가능) | ✅ (여러 번 요청해도 결과 동일)    |
| 리소스 위치 지정        | 클라이언트가 모름 → 서버가 생성   | 클라이언트가 명확히 지정          |
| 예시               | POST /users          | PUT /users/123         |
| 주로 쓰는 상황         | 새로운 게시글 등록, 댓글 추가    | 기존 정보 수정, 덮어쓰기 저장      |


`캐시 가능하다` 
- 서버의 응답을 로컬로 저장하여 재사용 가능하다. 
- PUT와 DELETE는 최신 결과를 받아야 하기 때문에 로컬에 저장하여 재사용할 수 없다. 

`리소스(Resource)란?`
**서버가 식별 가능한 형태로 관리하는 모든 데이터나 기능**
**예시 1: 블로그 웹사이트**
- /posts/1 → 글 1번 (리소스)
- /users/15 → 유저 15번 정보 (리소스)
- /comments → 댓글 목록 (리소스)
각각의 URL은 고유한 **리소스의 위치**이고, 우리가 이 리소스에 대해 GET, POST, PUT, DELETE 같은 HTTP 메서드를 사용하는 거야.

`멱등성이란?`
**요청을 여러번 보내도 서버의 상태가 변하지 않는 특성**
- POST는 동일한 요청을 여러 번 보내면 서버의 상태는 한 번 보낸 것과 다르게 변경될 수 있기 때문에 멱등하지 않다,

## 4. URI, URL, URN에 대해 설명해 주세요. 
- 인터넷에서 **자원**을 **식별**하는 **방식**에 대한 개념 
- uniform resource identifier(uri)
	- 상위 개념 
	- 자원을 식별하는 문자열 
- uniform resource locator(url)
	- 리소스의 위치를 나타내는 문자열 
	- 리소스에 접근하는 프로토콜(http://)을 포함 
	- 가장 구체적이고 명확
- uniform resource name(urn)
	- 자원의 이름을 나타내는 문자열 
	- 특정 명명 체계를 사용 

`url`
`scehma://[userinfo@]host][:port][/path][?query][#frament]`
ex)
	`https://lee.jun@www.example.com:123/forum/questions/?tag=networking&order=newest#top`
	- `https://` => schema : 사용할 프로토콜
	- `lee.jun` => userinfo : 인증 정보, username:password 형식으로 표현 ex) tommy:password@host.com과 같이 사용
	- `@www.example.com`=>host : 자원이 위치한 서버의 도메인 이름이나 ip 주소
		- example.com, 192.31.21
	- `:123`=>port : > 같은 IP 주소에서 다양한 서비스를 구분하기 위해 그리고 자원에 접급하기 위한 서버의 포트 번호 
		- 포트 번호는 특정 서비스로 **문을 두드릴 수 있는 입구**
		- 기본 포트 : http 80, https 443
	- `/forum/questions/`=>path : 서버 내부에서 리소스를 식별하는 경로 
		- /로 구분하며 계층적인 구조를 지님 
		- /images/logo.png
	- `/?tag=networking&order=newest`=>query : 리소스에 전달할 추가적인 정보 
		- key=value 형식의 쌍으로 표현, & 기호로 구분 
	- `#top`=>fragment : 리소스 내부에서 일종의 "책갈피" 역할을 하는 특정 부분을 카리키는 
		- 문서 안의 북마크처럼 작동
		- 예를 들어 스크롤을 특정 파트에 가게 한다던가 

`자원이란?`
- 인터넷 상의 무언가
- 서버에서 관리되는 **데이터나 기능** 주, 고유하게 식별가능한 것 
- 게시글, 유저, 상품, 이미지, 기능(API)

## 5. RestAPI에 대해 설명해 주세요.
- RestAPI는 클라이언트와 서버 간의 통신 방식을 정의한 Rest(REpresentational State Transfer)라는 아키텍처 스타일을 따르는 웹 API
- **웹의 자원을 HTTP 방식으로 표현하고 조작**하는 아키텍처 스타일
- 리소스는 JSON, XML, HTML 등의 다양한 형식으로 표현될 수 있으며 URI로 식별됨
- 캐싱, 계층화 시스템, 주문형 코드 등의 특징을 통해 시스템의 성능과 확장성을 향상 

핵심 구성요소
- **자원**: 서버가 관리하는 대상 (예: 사용자, 글 등)
- **URI**: 자원의 위치 (예: /users/1)
- **HTTP 메서드**: 자원에 대한 행위 (`GET`, `POST`, `PUT`, `DELETE`)
- **표현**: 자원을 주고받는 형식 (JSON, XML 등)
- **무상태성**: 요청 간 서버에 상태 저장 안 함

예시
| 메서드(HTTP) | 경로(URL) | 의미 |
|--------|------|------|
| GET | /posts/10 | 게시글 10번 조회 |
| POST | /posts | 새 게시글 생성 |
| PUT | /posts/10 | 게시글 10번 수정 |
| DELETE | /posts/10 | 게시글 10번 삭제 |
을 통해 json파일로 응답을 주고 사용자 컴퓨터에 전달함

`클라이언트-서버 구조`
- 클라이언트는 요청을 발생시키고, 서버는 REST API를 제공함으로써 요청에 대해 반응하는 구조 
- 클라이언트와 서버가 분리되어 서버로의 독립성과 확장성을 높임 

`무상태성(Stateless)`
- 클라이언트의 상태 정보를 서버에 저장하지 않고, 클라이언트는 각 요청에 필요한 정보를 모두 담아서 전송 

`캐시 가능성`
- HTTP 프로토콜의 캐싱 기능을 활용하여 자주 사용되는 데이터를 저장하고 재사용 
- 응답속도를 높임 

`계층화된 시스템`
- 클라이언트와 서버 사이에 여러 개의 중간 계층을 두는 것 

`균일한 인터페이스`
- 자원을 식별하고 조작하는 방식이 통일되어 있는 상태 

`자기 서술적 메시지`
- 요청과 응답 메시지에 필요한 정보가 모두 포함되어 있어서 메시지만으로 수행할 작업을 이해 

`Hypermedia as the engine of application state`
- 클라이언트가 현재 리소스와 연관된 다른 리소스에 접근할 수 있는 하이퍼링크를 제공 

#### `API 란`
- API(application programming interface)는 애플리케이션 또는 클라이언트와 서버 간에 데이터나 기능을 공유하기 위한 인터페이스 
- 소프트웨어끼리 통신하거나 기능을 사용할 수 있도록 만든 “**약속” 혹은 “통신 규칙”**
